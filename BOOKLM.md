# BookLM: сквозная модель и родословная артефактов

BookLM — сквозная модель книги. В главах 3–4 читатель собирает её по частям: токенизатор в главе 3,
внимание, блок и полный проход в главе 4. В конце главы 4 формы параметров замораживаются. Дальше каждая
глава либо меняет значения параметров, либо строит вокруг модели новый файл со ссылкой на родителя.

## 1. Что означает «одна модель»

До замораживания архитектуры BookLM — учебная конструкция: читатель по очереди добавляет токенизацию,
внимание, позиционное кодирование, нормализацию и полносвязный блок. Сохранённая родословная начинается с
`booklm-base-init` в конце главы 4: после этой точки формы параметров не меняются. Глава 5 сравнивает
BookLM с современными блоками, но саму модель не меняет; правило инициализации и затравку для
`booklm-base-init` окончательно задаёт глава 7.

Слова «та же модель» не означают, что все файлы побайтно одинаковы. Они означают, что любой производный
файл можно связать с родителем через манифест:

- дообученный файл содержит новые значения тех же параметров или отдельный адаптер;
- индекс поиска и набор инструментов ссылаются на модель, но не меняют её параметры;
- GGUF и ONNX являются производными представлениями одного контрольного сохранения;
- образ сервера указывает точную контрольную сумму модели, токенизатора и конфигурации выполнения.

Если связь с родителем или преобразование неизвестны, артефакт не относится к BookLM, даже если у него то
же имя файла.

## 2. Замороженная конфигурация BookLM-Base

| Свойство | Значение | Почему это полезно в книге |
|---|---:|---|
| Словарь | 8192 токена | логиты уже имеют реалистичную форму, но модель остаётся малой |
| Ширина скрытого состояния | 256 | все матрицы помещаются в память обычного компьютера |
| Число блоков | 6 | можно увидеть накопление состояния по глубине |
| Число голов запросов | 8 | размер одной головы равен 32 |
| Число голов ключей и значений | 2 | позволяет руками вывести групповое внимание и размер KV-кэша |
| Ширина промежуточного слоя | 768 | используется SwiGLU с тремя матрицами |
| Максимальная длина | 512 токенов | достаточно для лабораторий по памяти и поиску |
| Нормализация | RMSNorm | её можно полностью реализовать несколькими строками |
| Позиции | RoPE | позиция меняет запросы и ключи без таблицы позиционных векторов |
| Выходная матрица | общая с таблицей токенов | уменьшает число параметров и вводит связывание весов |
| Смещения в линейных слоях | отсутствуют | упрощают подсчёт и соответствуют многим декодерным LLM |

Точное число обучаемых скаляров — **6 622 464**:

```text
таблица токенов:       8192 × 256                         = 2 097 152
один блок внимания:    256×256 + 2·256×64 + 256×256      =   163 840
один блок SwiGLU:      3·256×768                          =   589 824
две RMSNorm в блоке:   2·256                              =       512
шесть блоков:          6·(163 840 + 589 824 + 512)        = 4 525 056
финальная RMSNorm:     256                                =       256
итого:                                                     6 622 464
```

В BF16 одни параметры занимают 13 244 928 байт, то есть примерно 12,63 МБ. Это ещё не полная память
обучения: градиенты, состояния оптимизатора, промежуточные значения и временные буферы считаются отдельно.

## 3. Один запрос и KV-кэш

Для одного токена один блок хранит два тензора — ключ и значение. В каждом по 2 головы по 32 числа. При
хранении в BF16 получается

```text
2 (K и V) × 2 головы × 32 числа × 2 байта = 256 байт на блок и токен.
```

Для шести блоков это 1536 байт на токен одного запроса, а для контекста из 512 токенов — 786 432 байта,
или 768 КБ. Этот расчёт становится инвариантом: учебная реализация KV-кэша, страничное размещение и сервер
должны сообщать одинаковое логическое число элементов, хотя физически могут хранить их по-разному.

Где эти узлы лежат в репозитории:

- файлами в `models/booklm/`: `booklm-tokenizer-v1` — `tokenizer.json`; `booklm-base-init` —
  `steps/step000000.pt`; `booklm-base-step-3051` — `booklm-base.pt` (промежуточные шаги — в `steps/`);
  `booklm-instruct-lora-v1` — `booklm-instruct-lora.pt`; `booklm-instruct-merged-v1` — `booklm-instruct.pt`;
  `booklm-hf-v1` — `hf/instruct-fixed/`;
- манифестами, которые ноутбуки пишут при запуске в `notebooks/artifacts/` (в репозитории этого каталога
  нет): `booklm-rag-v1` (ноутбук 12), `booklm-tools-v1` (13), `booklm-guarded-v1` (18);
- остальные узлы (порты главы 6, `prompt-v1`, `memory-v1`, GGUF, тернарная ветвь, ONNX, образ сервера,
  кластерный выпуск, `guarded-v2`) описаны в книге и строятся её опытами и ноутбуками, отдельных файлов
  для них в репозитории нет.

Мультимодальные порты ответвляются от замороженного ядра как спецификация интерфейса; звуковой тракт —
дочерняя спецификация конкретного входа. Промпт, память, RAG и инструменты меняют систему вокруг весов и
ответвляются от адаптерной версии, а файлы для выполнения (GGUF, ONNX, образ сервера) — от слитой.
Тернарная BookLM — отдельная ветвь обучения от той же инициализированной архитектуры, а не преобразование
готовых BF16-весов.

Вне основной родословной остаются:

- три запасных `config.json` главы 5 без весов: `booklm-mqa-spec-v1`, `booklm-window-spec-v1`,
  `booklm-moe-spec-v1`. Каждый отличается от BookLM одной деталью блока;
- расчёт MXFP4 в главе 14. Он не создаёт файла: для BookLM-MoE из главы 5 резидентная память
  составляет 32,9 МБ в BF16 и 13,1 МБ с экспертами в MXFP4 (`labs/ch14/moe_resident_memory.py`);
- главы 15 и 16. Они разбирают выполнение на GPU и распределённое обучение той же модели и новых узлов
  родословной не создают.

## 5. Манифест каждого опыта

Каждый узел родословной описывает маленький `manifest.json`: что это за файл, его SHA-256, родители и
проверки. Веса BookLM лежат в репозитории через Git LFS, а манифесты ноутбуки и опыты пишут при запуске.
Манифест пишет `make_manifest` из `labs/ch17/release.py`:

```json
{
  "id": "booklm-onnx-step-v1",
  "file": "booklm-onnx-step-v1.onnx",
  "format": "onnx",
  "sha256": "...",
  "parents": {"booklm-instruct-merged-v1": "..."},
  "transform": "export_onnx_step",
  "git_commit": "...",
  "python": "3.12.13",
  "torch": "2.14.1",
  "checks": {"max_abs_logit_diff": "..."}
}
```

В `parents` по записи на каждого родителя (у слитых весов их две). `labs/ch17/manifest_lineage.py` и ноутбук
`17_artifact_lineage.ipynb` строят по манифестам цепочку и проверяют её. Многоточия — места для чисел вашего
прогона. Глава 7 дописывает к манифесту данные, рецепт и метрики, глава 18 — поля `signature`, `sbom` и
`metrics` с результатами набора атак. Проверка обязана завершиться ошибкой, если SHA-256 родителя не совпал.

## 6. Два пути от ноутбука к кластеру

Книга не строит конфигурацию, где все названные инструменты обязательны одновременно. Она описывает два
пути, чтобы читатель увидел границы ответственности. Кода для Ray, Kubernetes и Nomad в репозитории нет:
эти шаги разобраны в главах 16 и 17 текстом и листингами, а для их запуска нужен настоящий кластер.

1. **Исследовательский и GPU-путь:** PyTorch → распределённое обучение → vLLM → Ray → Kubernetes.
   PyTorch определяет вычисление, vLLM управляет выполнением запросов, Ray размещает процессы модели, а
   Kubernetes управляет контейнерами и узлами.
2. **Переносимый путь:** PyTorch → ONNX → ONNX Runtime → контейнер → Nomad.
   ONNX задаёт граф и операторы, среда выполнения выбирает аппаратный поставщик вычислений, а Nomad
   размещает сервис и запрашивает GPU через механизм устройств.

Оба пути используют один набор функциональных тестов, один формат манифеста и один нагрузочный профиль.
Сравнение проводится не по числу YAML-файлов, а по корректности, задержке, пропускной способности,
использованию памяти, поведению при отказе и времени отката.
